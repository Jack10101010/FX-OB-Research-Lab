# Trade Universe — Notes To Future Jack

Read this before touching anything in `tradeUniverse.js`, `useTradeUniverse.js`, or any of the labs that show trade data. It's here to save you a day re-deriving why pages look the way they do.

If you only have 30 seconds: scroll to **These Rules Exist For A Reason** at the bottom, then bail. Come back when you actually have to change something.

---

## What's the Trade Universe?

It's the answer to **"which trade list is this page currently looking at?"**, expressed as one object with provenance attached.

```
{
  universeType: "baseline" | "scenario",
  label:        "Baseline" | "Triggered Edge 25% · Next" | …
  sourceKey:    "baseline" | "entry_triggered_edge_25p0_next" | …
  sourceFile:   "trades_allow_multi_position__entry_triggered_edge_25p0_next.csv"
  variant:      "allow_multi_position" | …
  scenario:     { family, threshold, fillMode },
  trades:       Trade[],
  stats:        summarizeTradeSanity(trades),   // canonical
  warnings:     [{ code, message }, …],
  canCompareToBaseline,
  baselineTrades,
  baselineStats,
}
```

The reason this exists at all is that two pages used to disagree about basic numbers. Run Detail's KPI said `10/20/+9.80R`, Strategy Map said `8/12/+10.97R`, you thought it was a bug, it was just **different CSVs**. Each surface was reading whatever trade list seemed convenient and they drifted.

The TradeUniverse pins down (a) which trade list, (b) where it came from, (c) what universe type, (d) any warnings about how it was resolved. Every consumer is now wired to one shape.

## Run → Scenario → Trade Population

A run is a bundle of CSVs the backend produced. Inside that bundle, the trade lists you can pick from form a small tree:

```
Run  20260528_114220_EURUSD_15min_RR3.3_SB1
│
├── Baseline                                        ← primary variant CSV
│   trades_allow_multi_position.csv
│   35 rows · 10W / 20L · +9.80R · 0 protected
│
├── Triggered Edge · 25% · Same                    ← scenario CSV
│   trades_…__entry_triggered_edge_25p0_same.csv
│   35 rows · 8W / 18L · +4.46R · 4 protected
│
└── Triggered Edge · 25% · Next                    ← scenario CSV
    trades_…__entry_triggered_edge_25p0_next.csv
    35 rows · 8W / 12L · +10.97R · 10 protected
```

Same OBs in all three lists, but different outcomes per OB because the entry model fires at different prices (and sometimes refuses to fire at all — those rows become **PROTECTED**, the page-friendly name for `INVALID_CANCELLED` / `outcome == "INVALID"`).

A **scenario** is just `(family, threshold, fillMode)`:
- `family`: `"baseline"` | `"triggered_edge"` | `"penetration"` | (future entry models)
- `threshold`: `25` | `50` | `10` | … (percent of OB penetration)
- `fillMode`: `"same"` | `"next"` | `null` (combined CSV; rare)

`buildCanonicalKey(family, threshold, fillMode)` turns those into the importer key like `entry_triggered_edge_25p0_next`.

## Page Categories

Every page that touches trade data belongs to exactly one of three buckets.

| Category | Pages | Why |
|---|---|---|
| **Scenario-aware** | Strategy Map · Failures Lab · Hypothesis Lab · Trade Inspector · News Lab · Order Block Lab · Overview (scope toggle = "Active scenario") | These pages should reflect whatever the user picked in Strategy Map. Numbers re-flow when scenario changes. |
| **Baseline-only by design** | Run Detail · Protection Lab · Comparison Lab · Overview (scope toggle = "Baseline reference") | Switching their trade source to active scenario would break the page's actual job. They show a baseline scope chip explaining themselves. |
| **Run-list / synthetic** | Runs · Projects · Sweep Lab · Monte Carlo · Walk Forward Lab · Parity Debugger · Strategy Builder | Not really trade-data pages. They list runs, run sweeps, or use synthetic data. Nothing to migrate. |

Strategy Map is the **source** of scenario state. The user clicks a pill there. Everyone else reads `state.scenario`.

## Why ProtectionLab Is Different

Protection result CSVs are exported by the backend **against the baseline trade list**. The file `trades_allow_multi_position__close_confirmed_breach.csv` was generated by running the close-confirmed protection rule over the 35 baseline rows of `trades_allow_multi_position.csv`. Each protection-mode trade has an `ob_id` that matches a baseline OB.

If Protection Lab suddenly used a different baseline (say Triggered Edge 25% Next), the page would compare:

```
"Unprotected baseline":      TE-Next  ← user just changed this
"Protection mode close_…":   baseline ← didn't change, can't change
```

The pairing logic (`buildPairedTrades`) joins on OB id. OB 12 in TE-Next is `INVALID` (PROTECTED, 0R). OB 12 in `close_confirmed_breach` was a baseline LOSS that the protection rule caught. The page would happily report "close_confirmed_breach saved you 1.0R on OB 12" — but you weren't even going to trade OB 12 under TE-Next, so the protection rule saved you nothing.

**Concrete example.** Baseline has 18 losses. TE-Next has 12 losses (10 became PROTECTED by the entry model). If you let Protection Lab pretend TE-Next is its baseline, the protection table would show protection-mode "wins" against losses that wouldn't have happened in the first place.

Protection Lab stays baseline-only **until the backend re-exports protection results against each entry scenario** (`trades_<variant>__<entry_key>__<protection_mode>.csv`). That's a backend project, not a frontend one.

## Why ComparisonLab Is Different

ComparisonLab compares **runs** against each other, not scenarios. Today it shows:

```
Run A baseline   vs   Run B baseline   vs   Run C baseline
```

If you made it scenario-aware, the first ambiguity is: "compare them all at the user's currently-active scenario, or compare each run at its own preferred scenario?". Then the second: what do you show for a run that doesn't have that scenario? Run A was backtested last week with Triggered Edge available. Run B was backtested six months ago, baseline only. Pick TE-Next as the global comparison scenario and Run B becomes "scenario unavailable, falling back to baseline". That's a UX design problem.

**Phase 3C plan** (when you eventually do this):

```
COMPARE AT  [ Baseline ]  [ Triggered Edge 25% · Same ]  [ Triggered Edge 25% · Next ]  [ Penetration 10% ]
            ────────────                                                                                ↑
            (default)                                                                          user picks one

For each run row:
  universe = getTradeUniverse(run.id, globalScenarioChoice)
  if universe.warnings.includes("SCENARIO_NOT_AVAILABLE_FOR_RUN"):
      show row with "Baseline fallback" chip, muted colors
  else:
      compare normally
```

Two things you'd need to add to `tradeUniverse.js`:
1. `equityCurve` (and `monthly`) lazy-derived on the universe — ComparisonLab needs them per-row.
2. A `SCENARIO_NOT_AVAILABLE_FOR_RUN` warning code.

Until that's worth doing, ComparisonLab stays baseline-only with a scope chip saying so.

## Resolution Flow

This is what happens between "user clicks a pill in Strategy Map" and "the badge on Failures Lab updates":

```
┌────────────────────────────────────────────────────────────────────┐
│  User clicks a scenario pill in Strategy Map                       │
│  e.g. "Triggered Edge 25%" + "Next"                                │
└──────────────────────┬─────────────────────────────────────────────┘
                       ▼
┌────────────────────────────────────────────────────────────────────┐
│  ScenarioSelector → onScenarioChange({family, threshold, fillMode})│
│  store.js: setScenario(patch)                                      │
│  state.scenario merged                                             │
│  notify() → every useDataset() subscriber re-renders               │
└──────────────────────┬─────────────────────────────────────────────┘
                       ▼
┌────────────────────────────────────────────────────────────────────┐
│  Consumer page renders                                             │
│  useTradeUniverse() runs                                           │
│   ├─ subscribes via useDataset()                                   │
│   └─ memoizes getTradeUniverse(runId, scenarioOverride)            │
└──────────────────────┬─────────────────────────────────────────────┘
                       ▼
┌────────────────────────────────────────────────────────────────────┐
│  store.getTradeUniverse(runId, override)                           │
│   bundle    = state.runs[activeRunId]                              │
│   scenario  = override ?? state.scenario                           │
│   fallback  = state.selectedTradeVariant ?? bundle.primaryVariant  │
│   →  resolveTradeUniverse({ bundle, scenario, fallbackVariant })   │
└──────────────────────┬─────────────────────────────────────────────┘
                       ▼
┌────────────────────────────────────────────────────────────────────┐
│  tradeUniverse.resolveTradeUniverse                                │
│   1. pickVariant(...)                                              │
│   2. collectAllEntryKeys(...) + buildAvailableOptions(...)         │
│      ← "both" only added when a real bare CSV exists               │
│   3. resolveHierarchy(scenario, hint, allKeys, options)            │
│      ← coerces fake "both" to "next" (or "same") with a warning    │
│   4. buildCanonicalKey(family, threshold, fillMode)                │
│      → e.g. "entry_triggered_edge_25p0_next"                       │
│   5. selectTrades(canonicalKey, fillMode, bundle, baseTrades)      │
│      → reads bundle.entryResults.tradesByMode[<key>]               │
│   6. summarizeTradeSanity(trades) → universe.stats                 │
│   7. Attach warnings:                                              │
│        FILL_MODE_COERCED                                           │
│        BOTH_UNAVAILABLE_NO_COMBINED                                │
│        NO_TRADES_FOR_SCENARIO                                      │
│   8. Compute sourceFile (filename or best-effort guess)            │
│   9. Compute baselineTrades / baselineStats for comparison         │
└──────────────────────┬─────────────────────────────────────────────┘
                       ▼
┌────────────────────────────────────────────────────────────────────┐
│  Consumer page receives a fully-resolved TradeUniverse object      │
│   - trades drive charts / lists / filters                          │
│   - stats drive KPI cells                                          │
│   - warnings render as chips inside <TradeUniverseBadge />         │
└────────────────────────────────────────────────────────────────────┘
```

For pages that pin to baseline (Protection Lab, Comparison Lab, Overview's baseline scope), step 3 short-circuits because the caller passes `{ family: "baseline" }` as the override. The badge always says `Baseline / trades_<variant>.csv`.

## These Rules Exist For A Reason

Each of these has at least one audit phase behind it. Don't break them lightly.

**1. Use `useTradeUniverse()` whenever a page touches trade data.**
This is the canonical entry point. You get scenario-awareness, memoization, warnings, and stats that match every other page in the app.

**2. Don't destructure `TRADES` from `useDataset()` in a new page.**
`TRADES` is the active variant's primary baseline. It silently ignores the user's selected scenario. Every time someone has done this, the page eventually drifts.

**3. Protection Lab is baseline-only on purpose.**
See the section above. Don't try to "fix" it by wiring scenario state in. The protection result CSVs aren't compatible.

**4. Comparison Lab is baseline-only on purpose.**
See the section above. Phase 3C is the right time to make it scenario-aware, not a casual afternoon.

**5. Don't add a "protection universe" inside `tradeUniverse.js`.**
Protection modes are not entry-model scenarios. They're a parallel concept. If they ever need a resolver, write `protectionUniverse.js` next door. Conflating them muddies the resolver semantics that took five phases to settle (1, 2A, 2B, 2C, 3A).

**6. `getTradeUniverse(runId, override)` is for multi-run code.**
`useTradeUniverse()` always resolves the active run. ComparisonLab Phase 3C will call `getTradeUniverse(r.id, …)` per row. Don't use it inside a single-active-run page.

**7. Fake "Both" must stay disabled.**
`buildAvailableOptions` only adds `"both"` to a (family, threshold) pair when a bare combined CSV exists in the bundle. When the user clicks "Both" anyway and there's no combined CSV, `resolveHierarchy` coerces to `"next"` (then `"same"`) and attaches `FILL_MODE_COERCED`. **Never** silently union same + next — that's the 70-rows-from-a-35-row-run bug Phase 1 fixed. The dedup key is `entry_model_key + trade_id` and `_same` vs `_next` is in the key, so the dedup is a no-op. The union just doubles everything.

**8. Use `summarizeTradeSanity` for PF, DD, WR.**
Not `computeProfitFactor` / `computeMaxDrawdown` from `lib/metrics.js`. The numbers agree on clean data but the lib/metrics versions don't gate on canonical category — a stale non-zero R on an UNFILLED row drifts the PF. The only legitimate consumer of `lib/metrics.js` left is Comparison Lab; everything else uses canonical.

## Things You Will Probably Forget

### "Baseline" means three different things.
- In `tradeUniverse.js` it's the primary-variant CSV (no entry-model overlay).
- In Protection Lab it's the **unprotected** reference (no protection rule applied).
- In Comparison Lab "Run A is the baseline" means the first run in the comparison set.

All three are valid in context. `TradeUniverseBadge` always shows meaning #1. If you see "Baseline" on a Protection Lab screenshot and you're not sure which kind, it's the protection one.

### The scenario state is in the store, not in any page.
`state.scenario` lives in `store.js`. Strategy Map writes it via `setScenario()`. Every page reads it via `useDataset() → state.scenario` or via `useTradeUniverse()`. There's no per-page scenario state (and there shouldn't be, except in ComparisonLab Phase 3C).

### Two `useTradeUniverse()` calls in one component is fine.
Overview does it: one for the active scenario, one with `{ family: "baseline" }` override. The resolver is pure and memoized. The cost is two `summarizeTradeSanity` calls per render. Not a perf concern on 35-row runs, barely measurable on 50k-row ones.

### `useDataset()` and `useTradeUniverse()` together is fine.
React batches the subscriptions. The badge takes the universe; non-trade fields (`ACTIVE_RUN`, `ACTIVE_TRADE_VARIANT`, `activeRunId`, `runs`) come from `useDataset()`. Both subscribe to the same store.

### `protectionResults.tradesByMode` is sibling to `entryResults.tradesByMode`, not a member.
They live in the same bundle but represent different concepts. Don't try to model protection modes as a `tradeUniverse.js` family — they don't have thresholds or fill modes, the abstraction would leak.

### Scenario-aware analytics aren't finished.
Done: Failures, Hypothesis, Trade Inspector, News, Order Block, Overview.
Not done: Protection (backend blocker), Comparison (UX blocker), Run Detail (intentional reference).
Don't be surprised when ComparisonLab numbers don't move while everything else does.

### The TradeUniverseBadge is a contract statement.
Every consumer page shows it near the top. If a user is confused why two pages disagree on numbers, the badge's `SOURCE` cell is the answer. The badge isn't decoration — it's the "you are here" sign for trade data.

### `summarizeTradeSanity` is the source of truth for stats.
Wins, losses, win rate, profit factor, max drawdown, gross win R, gross loss R, expectancy — all canonical. PF returns `Infinity` on no-losses (the badge renders this as `∞`); `lib/metrics.computeProfitFactor` returns `null` for the same case. They drift on data anomalies. Always prefer canonical.

## Common Mistakes I'm Going To Make

```js
// Wrong: first arg is runId, not scenario.
useTradeUniverse({ family: "baseline" })

// Right:
useTradeUniverse(null, { family: "baseline" })
```

```js
// Wrong: destructuring TRADES kills scenario-awareness.
const { TRADES } = useDataset();
const filtered = TRADES.filter(...);

// Right:
const universe = useTradeUniverse();
const filtered = universe.trades.filter(...);
```

```jsx
// Wrong: per-page warning filter, defeats the whole point of Phase 2G.
const universeWarnings = (universe.warnings || []).filter(w => (
  w.code === "BOTH_UNAVAILABLE_NO_COMBINED" || w.code === "FILL_MODE_COERCED"
));
<TradeUniverseBadge universe={universe} warnings={universeWarnings} />

// Right (badge filters internally):
<TradeUniverseBadge universe={universe} />
```

```js
// Wrong: assuming PF will be a number.
const pf = stats.profitFactor;
const display = pf.toFixed(2);     // "Infinity"

// Right:
const display = stats.profitFactor == null
  ? "N/A"
  : Number.isFinite(stats.profitFactor) ? stats.profitFactor.toFixed(2) : "∞";
```

```jsx
// Wrong: trying to add scenario awareness to Protection Lab.
const universe = useTradeUniverse();
const trades = universe.trades;       // ← contaminates the unprotected baseline
const p = buildProtection(trades);

// Right: keep TRADES (baseline) for analytics. Badge stays pinned to baseline.
const { TRADES } = useDataset();
const trades = TRADES;
const baselineUniverse = useTradeUniverse(null, { family: "baseline" });
<TradeUniverseBadge universe={baselineUniverse} />   // badge only
```

If you forget where the moving parts live:

```
frontend/src/data/
├── tradeClassification.js   → classifyTrade, summarizeTradeSanity, displayOutcomeLabel
│                              The "what category is this trade" + "what label do I show" layer.
├── tradeUniverse.js         → resolveTradeUniverse, resolveBaselineUniverse,
│                              describeTradeUniverse, plus all the pure helpers
│                              (familyFromKey, extractThreshold, fillModeFromKey,
│                               collectAllEntryKeys, buildAvailableOptions,
│                               resolveHierarchy, selectTrades).
├── useTradeUniverse.js      → React hook. The only entry point pages should use
│                              for scenario-aware trade data.
├── store.js                 → useDataset, getRunData, getTradeUniverse,
│                              setScenario, setActiveRunId, etc.
└── README.md                ← you are here
```

UI:
```
frontend/src/components/lab/
├── TradeSanityStrip.jsx     → reusable W/L/Net R/PF/DD strip on top of summarizeTradeSanity
└── TradeUniverseBadge.jsx   → shared Universe/Model/Variant/Source/Rows badge
```

Strategy Map's own resolver (chart-specific things on top of the shared resolver):
```
frontend/src/pages/strategyMap/
├── useResolvedScenario.js   → React hook; imports helpers from tradeUniverse.js
│                              and adds chart-specific derivations (RR tools,
│                              triggered-edge overlays, OB enrichment).
└── ScenarioSelector.jsx     → the pill picker UI; writes to state.scenario.
```
